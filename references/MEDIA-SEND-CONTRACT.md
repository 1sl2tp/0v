# 0v independent media send — proposed contract (not deployed)
26/11/2026 VN. L06. Evidence from read-only catalog inspection: public.v0_admin_read, v0_admin_media, v0_admin_send_text exist; no 0v upload/commit RPC. Existing public.v21_media_assets_send(p_app_session_id,p_conversation_id,p_client_id,p_body,p_assets) requires v21_private.require_active_account. Storage v21_media_insert_member_image calls v21_storage_private.can_upload, requiring v21_sessions. Do not reuse old app session or relax policy globally.

## Proposed sequence (next backend review)
1. On explicit Send, freeze contact, authenticated account/session, stable client UUID, text and ordered immutable asset IDs/MIME/size. Same key for retry, no automatic retries on ambiguous commit. No network call on picker selection.
2. Separate prepare RPC authenticates an active admin and AAL2/session, verifies eligible contact and membership, creates/finds room if necessary, reserves exact asset IDs and canonical storage paths account/room/asset in private expiring tickets. No message insert in prepare. Exact replay returns same reservations; changed body/contact/manifest rejects. Ticket table in private schema; deny direct access.
3. Private v21-media upload policy limited to matching pending ticket, authenticated uploader, exact object key and expiry; no broad grants/upsert/public URL. Actual object bytes, allowed MIME/size and integrity must be verified server-side before publication; metadata alone is insufficient for malicious file content. Storage failures keep the draft. Cleanup expired, uncommitted objects via authorized server Storage API, not direct SQL deletes.
4. Commit RPC rechecks account/session/AAL2/contact and exact ticket ownership; locks batch, checks storage object owner/size/MIME, existing canonical message/client ID and all assets. In one transaction create message plus assets, mark committed, return canonical IDs. Retry after response loss returns same committed IDs only; never append different assets to an existing message or update a deleted one. Different text/contact/asset manifest rejects. Do not mark sent before canonical ack.
5. Reuse canonical messages/media and existing trigger/outbox infrastructure after staging proof. Insert triggers currently include v21_messages_emit_sync, enqueue_zalo_outbound, enqueue_admin_push; media emit_sync, enqueue_zalo_media_outbound and chat_bank_bill_queue_amount. Verify no duplicate pushes, no empty text Zalo delivery, no automatic bank collection from admin image, no visible incomplete media on sync, no real sends during tests.
6. UI keeps DraftMedia and Main/ScrollController. On acknowledged send, clear only frozen matching draft assets; room switch/logout invalidates UI result. On failure keep bytes and user draft. Realtime reconciliation separate.

## Scope and constraints
Observed old RPC supports image/audio/file, max 12 assets, 15 MiB each; file allowlist PDF, text/plain, CSV, Word/Excel old/new. New draft UI deliberately keeps existing 8 asset cap, no video send (requires canonical schema/provider decision), no automatic recording or background uploads. Image dimensions <=20000, optional duration <=3600000ms for audio; exact values validated server-side. No production SQL migration prepared or applied in this release. 
## Required staging proof before backend activation
- Guest, non-admin, locked/deleted account, expired session, AAL1, foreign contact/room, changed or expired ticket -> denied.
- Wrong path, wrong object owner, missing object, wrong size/MIME, duplicate asset IDs, unsupported type, oversize -> no message.
- Concurrent same request/ack-loss replay -> exactly one message + exact same asset set; changed body/contact/manifest -> conflict; media vs text client key conflict rejected.
- Partial upload, logout, room switch, cancellation, expired ticket and cleanup -> no committed message or dangling accessible objects.
- Transaction rollback and trigger side effects tested with synthetic accounts and disabled external delivery; validate real Zalo/Push/Bank contract separately before go-live.
- Schema grants/RLS review, isolated DB fixture and browser fixture, explicit production rollout separate from UI release. Existing legacy API untouched.
